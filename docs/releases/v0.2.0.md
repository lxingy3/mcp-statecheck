# mcp-statecheck v0.2.0

This release brings the modern protocol to the installed CLI and makes saved
checks useful for reviewing server upgrades.

- Run `check --protocol-version 2026-07-28` against one explicit stdio or
  Streamable HTTP server. Discovery checks the advertised revision before
  fetching the tool list. Servers without a tools capability finish after
  discovery.
- Save a check before and after an upgrade. `mcp-statecheck compare baseline.json
  current.json` reports changes to tool names and to input and output schemas
  without connecting to either server. CI can use exit code 1 to require review
  of a changed catalog and exit code 2 to flag invalid or incomparable input.
- The package adds the controlled Tasks and subscription checks developed
  since v0.1.0, including native client delivery, recovery, and cancellation
  isolation across the pinned Python and TypeScript SDKs.

Existing `check` invocations keep their legacy default. JSON trace schema v1
remains the input to the offline report and replay commands. Catalog
comparison requires one complete tool list from each run. Use the same
protocol, transport, and authorization scope for both runs. It reports
structural differences without deciding whether a schema change is breaking.

## Build and verify

From a clean checkout with Python 3.12.13, Node.js 24.14.1, and uv:

```console
uv sync --locked
uv run pytest -q
uv run python scripts/run_m4_acceptance.py --output dist-evidence.json --dist-output dist
uvx --from twine==7.0.0 twine check --strict "dist/*"
```

The acceptance script installs the wheel and source distribution outside the
checkout. Both installations run modern checks over both transports and
compare their saved catalogs. The script also verifies the controlled replay
recipes, pinned SDK matrices, report formats, and cleanup from the previous
release.

The GitHub Release workflow defaults to a build and package check. Publishing
requires a separate dispatch with `publish` enabled on a tag that matches the
package version and points to a commit on `main`. The GitHub release uses the
verified distributions from that run, and the PyPI job uses trusted publishing.
